# Аудит архитектуры репозитория `sonata_launcher_core`

Дата аудита: 2026-07-20. Ветка: `feature/java-manager`. Объём: ~6 500 строк Rust, ~70 файлов.

Аудит охватывает архитектуру, организацию кода, именование, дублирование и мёртвый код. Бизнес-логика и алгоритмы не оценивались, кроме случаев, когда они влияют на архитектуру. Каждая находка помечена критичностью: **критично** / **желательно** / **косметическое**.

Целевая архитектура (со слов автора): модульность обеспечивается на уровне лаунчера — ядро с фиксированным API, фронтенд любой. Ядро планируется разделить в одной кодовой базе на два cargo-feature: **rust-библиотека** (для нативных rust-фронтендов, прямые вызовы без HTTP) и **веб-сервер** (для остальных клиентов). Оценки критичности в отчёте выставлены с учётом этого плана.

---

## 1. Резюме

Кодовая база находится в середине миграции между двумя поколениями архитектуры, и это — источник большинства проблем:

- **Старое поколение**: metacache.json, статические функции с `Result<_, String>`, логика прямо в хендлерах, `println!`-отладка.
- **Новое поколение**: SQLite + sqlx, модуль `java` с вертикальным срезом `model / error / service / storage / registry`, типизированный WS-протокол с ts-rs биндингами, реестры с broadcast-уведомлениями.

Новое поколение спроектировано заметно лучше, но переход не завершён: в дереве лежат осиротевшие файлы старой реализации, которые даже не компилируются; модуль `instance` не переведён на паттерн `java`; знание о раскладке каталогов и источниках манифестов размазано по 3–4 местам каждое.

Пять самых важных системных проблем (детали в соответствующих разделах):

1. **Осиротевший мёртвый код** — `src/java/parse/`, `src/utils/system.rs`, `src/utils/metacache/` не участвуют в компиляции или не используются (§2).
2. **HTTP/WS-транспорт протащен в доменный слой** — `EndpointRequest` и `WebSocketConnection` доходят до SQL-запросов; это прямой блокер запланированного разделения на библиотеку и сервер (§6.1).
3. **Два параллельных механизма прогресса** — внутренний реестр Tasks и `OperationWsMessage` обновляются вручную и независимо (§6.2).
4. **Продублированный конвейер загрузки** libs/assets — два почти идентичных пайплайна «проверить кэш → скачать → зарегистрировать» (§3.1).
5. **Лайфтайм `'a` в глобальном состоянии** — `GlobalDataState<'a>` заражает лайфтаймом весь стек из-за `Task<'a>` с заимствованными строками (§6.3).

## 2. Мёртвый и осиротевший код

### 2.1. `src/java/parse/` — осиротевшая директория целиком — **критично**

- **Что не так.** Файлы `src/java/parse/arch.rs`, `download.rs`, `extract.rs` не объявлены в `src/java/mod.rs` — объявления `pub mod arch/extract/download` там закомментированы (`src/java/mod.rs:5-7`). Файлы ссылаются на типы `Java` и `EntryInfo` из `super`, которых больше не существует. Это остатки старой реализации установки Java через metacache.json, полностью заменённой связкой `service.rs` / `storage.rs` / `registry.rs`.
- **Почему проблема.** Файлы не компилируются и не могут быть просто «включены обратно». Они создают ложное впечатление, что функционал скачивания Java существует, засоряют поиск по коду и грепы (например, три реализации детекции OS/arch, см. §3.6).
- **Как исправить.** Удалить директорию `src/java/parse/`. Если функционал скачивания Mojang-runtime планируется — писать заново поверх `JavaService`/`JavaStore` (старый код опирается на metacache.json, который уже мёртв). История останется в git.

### 2.2. `src/utils/system.rs` — файл-сирота — **критично**

- **Что не так.** Файл не объявлен в `src/utils/mod.rs` (там объявлены только `db`, `download`, `maven`, `metacache`, `unify`) и не участвует в компиляции. При этом содержит полезные `detect_os()` / `detect_arch()`.
- **Почему проблема.** Это третья (наряду с `construct_os_name` в `src/instance/download/libs/mod.rs:137` и мёртвым `java/parse/arch.rs`) реализация определения OS/архитектуры. Читатель не может понять, какая из них «настоящая».
- **Как исправить.** Два варианта: (а) удалить файл; (б) — предпочтительно — подключить его и сделать единственной точкой детекции системы, переписав `construct_os_name` как маппинг `(OsType, ArchType) -> &str` поверх него. Вариант (б) лучше: enum-представление типобезопаснее строк и понадобится и для libs, и для будущего скачивания Java.

### ✔️ ~~2.3. `src/utils/metacache/` — неиспользуемый модуль — **критично**~~

- **Что не так.** Модуль объявлен в `utils/mod.rs:12`, но ни одного вызова `metacache::` в живом коде нет — только в закомментированном импорте `src/java/mod.rs:9`. Это инфраструктура эпохи metacache.json, вытесненная SQLite.
- **Почему проблема.** Мёртвый код с активным объявлением — хуже сироты: он компилируется, поддерживается компилятором и выглядит как рабочая подсистема.
- **Как исправить.** Удалить вместе с полем `metacache_file` из `InstancePaths` (см. §2.10).

### ✔️ ~~2.5. `DEFAULT_JAVAREG_CACHE_SIZE` — объявлена, импортирована, не используется — **желательно**~~

- **Что не так.** Константа объявлена в `src/data/registry/mod.rs:6`, импортирована в `src/data/mod.rs:10`, но `JavaService::new` (`src/java/service.rs:21`) хардкодит `100`.
- **Почему проблема.** Читатель находит константу, считает её действующей конфигурацией, меняет — и ничего не происходит. Плюс константа java-кэша лежит в `data/registry`, хотя сам кэш живёт в `java/registry.rs` — не то место.
- **Как исправить.** Перенести константу в `src/java/registry.rs` (или `service.rs`) и передавать её в `JavaRegistry::new`; убрать импорт из `data/mod.rs`.

### 2.6. `JavaRegistry` — кэш, который пишется, но не читается — **желательно**

- **Что не так.** `JavaRegistry::retrieve()` и `touch()` (`src/java/registry.rs:33,67`) не вызываются нигде. Единственное использование реестра — `insert` при регистрации внешней Java.
- **Почему проблема.** LRU-кэш без читателей — это чистые накладные расходы и ложный сигнал о том, что чтение Java идёт через кэш. Судя по ветке (`feature/java-manager`), это задел под запуск инстансов с выбранной Java — но пока `LaunchInfoBuilder::build` делает `todo!("Implement default Java runtime")` (`src/instance/launch/mod.rs:147`).
- **Как исправить.** Это оправданный задел, если подключение планируется в этой же ветке — тогда просто довести до использования. Если нет — пометить `// TODO` с описанием плана, чтобы отличать задел от забытого кода.

### 2.7. Крупные закомментированные блоки — **косметическое**

- `src/endpoint/java.rs:11-44` — ~30 строк старого `download_java_ws`;
- `src/main.rs:8,28,54-55,78` — закомментированные роуты и модуль `config`;
- `src/websocket/messages/option/mod.rs:23-59` — старый ручной `impl Serialize`;
- `src/instance/launch/execute.rs:61-92` — пачки закомментированных аргументов запуска;
- `src/java/mod.rs:1-9` — закомментированные импорты и модули.

- **Почему проблема.** Закомментированный код не рефакторится вместе с живым и быстро протухает; git и так хранит историю.
- **Как исправить.** Удалить. Если блок — памятка о будущем функционале, заменить на однострочный `// TODO:` с сутью.

### 2.8. Протокольные типы, которые ядро никогда не отправляет — **косметическое / информационно**

`OperationUpdate::SingleDeterminable` (`event.rs:34`), `OperationFinish` + `OperationStatus` (`event.rs:62-81`), `ProgressUnit` (`progress.rs`), `DirStatus` (`process.rs:70`), `ProcessTarget::Dir`/`Instance`, `OperationStage::VerifyFiles`/`CreateStructure`/`ScanInstances`, `TaskStatus::CancelledAwaiting`/`Cancelled`.

- **Что не так / почему это скорее нормально.** Эти типы нигде не конструируются, но экспортируются в TypeScript-биндинги. Поскольку граница модульности лаунчера — API ядра, проектирование протокола «наперёд» (клиент готов к сообщениям, которые ядро научится слать позже) — оправданная практика, удалять их не нужно. После сплита (§6.1a) эти же типы станут публичной моделью событий библиотеки для нативных фронтендов, что дополнительно оправдывает их существование. Единственная проблема — задел не задокументирован и неотличим от мусора.
- **Как исправить.** Ничего не удалять; зафиксировать статус протокола в комментарии модуля `websocket/messages` (какие сообщения реально шлются сегодня). Примечательно, что `OperationFinish` выглядит именно забытым: `Instance::init` завершает операцию через `complete_stage` последней стадии, но событие завершения операции целиком не шлёт.

- `collect_code.sh` — вспомогательный скрипт, генерирующий `all_code.txt`. Не относится к продукту. Перенести в `scripts/` или удалить.
- `dev.db` — локальная база данных в рабочем дереве. Убедиться, что она в `.gitignore` (сейчас файл присутствует в дереве как untracked) — базы данных не должны попадать в git.

### 2.10. Легаси-поля `InstancePaths` — **желательно**

- **Что не так.** В `src/instance/paths/mod.rs:8-19` поля `instance_manifest_file`, `instances_list_file`, `headers`, `metacache_file`, `root` — их геттеры не вызываются нигде в живом коде. `headers/main.json` и `metacache.json` — раскладка старой JSON-эпохи.

## 3. Дублирование и кандидаты на объединение

### 3.1. Конвейер загрузки libs и assets — главное дублирование — **критично**

- **Что не так.** `src/instance/download/libs/{download,register}.rs` и `src/instance/download/assets/{download,parse,register}.rs` реализуют один и тот же пайплайн: выбрать кэшированные записи из БД → вычислить отсутствующие по hash → качать пачками через `FuturesUnordered` + `BufferPool` → `process_futures` с отправкой прогресса в WS → INSERT скачанного в БД. Дублируются даже константы `CONCURRENT_TASKS_COUNT = 100` и `CONCURRENT_BUFFERS_SIZE = 16 * 1024` (`libs/download.rs:13-14` и `assets/download.rs:10-11`), и функция `process_futures` (`libs/download.rs:139`, `assets/parse.rs:10`; третья копия — в мёртвом `java/parse/extract.rs:45`).
- **Почему проблема.** Любая правка (ретраи, лимиты, обработка ошибок, прогресс) должна вноситься дважды; копии уже разошлись в деталях (libs собирает classpaths/natives, assets — нет), что маскирует общую основу. Будущее скачивание Java-runtime станет третьей копией.
- **Как исправить.** Трейт `Downloadable` (`src/utils/download/mod.rs:39`) уже существует и реализован обоими `LibInfo` и `AssetInfo` — основа готова. Вынести в `utils/download` (или новый модуль `sync`) обобщённый компонент вида:
    ```rust
    async fn sync_missing<T: Downloadable>(
        needed: Vec<T>,
        cached_hashes: HashSet<String>,
        progress: &dyn ProgressSink,   // см. §6.2
    ) -> SyncOutcome<T>
    ```
    Специфика (SQL-запросы выборки/регистрации, сбор classpaths) остаётся в libs/assets, а очередь задач, пул буферов, `process_futures` и прогресс — общие.

### 3.2. Конструирование `ScanMessage` с заглушками — три копии — **желательно**

- **Что не так.** В `src/data/registry/instance/operations.rs` блок «`WsMessage::from(ScanMessage { base: BaseMessage { message_id: "asd", ... }, data: ScanData { ... ScanInfo { id, name, version, loader } } })`» повторён трижды: `update_instance_name` (:52), `add_instance` (:102), `get_all_instances_json` (:142). Все три — с плейсхолдерами `"asd"` вместо реальных id.
- **Почему проблема.** 60+ строк копипасты на 170-строчный файл; при изменении формата сообщения нужно править три места; заглушки `"asd"` уходят реальному клиенту.
- **Как исправить.** Два строительных блока: `BaseMessage::new(request_id: Option<String>) -> Self` (генерирует `message_id`/`timestamp`; сюда же пригодится неиспользуемая зависимость `uuid`, см. §8) и `impl From<&InstanceDataRow> for ScanMessage` (или метод `to_scan_message()`). Тогда каждое из трёх мест сожмётся до 2–3 строк.

### 3.3. Broadcast-обвязка Tasks и Instances — параллельные копии — **желательно**

- **Что не так.** `Tasks` (`src/data/registry/task/mod.rs`) и `Instances` (`src/data/registry/instance/mod.rs`) — структурные близнецы: `*_map: Arc<Mutex<HashMap<...>>>` + `notifier: Sender<Value>` + `_receiver`. Их операции тоже зеркальны: `create_task_broadcast`/`create_instance_broadcast` идентичны построчно, `add_task`/`add_instance`, `get_all_tasks_json`/`get_all_instances_json`, а WS-диспетчеры `debug_tasks` (`main.rs:91`) и `instance_dispather` (`endpoint/instance.rs:87`) — одна и та же петля «отправить всё → подписаться → ретранслировать».
- **Почему проблема.** Копипаста уже породила баг: `create_instance_reciever` подписывается на **tasks**-notifier (`data/registry/instance/operations.rs:21-23` — `self.data.tasks.notifier.new_receiver()`). Это классический симптом дублирования: копию поправили не полностью.
- **Как исправить.** Обобщить в `Registry<K, V>` (map + notifier + `subscribe()` + `broadcast_json()`), либо как generic-структуру, либо как общий внутренний тип с двумя обёртками. WS-петлю ретрансляции вынести в одну функцию `relay_broadcast(ws, receiver, initial: Vec<Value>)` в `websocket/`.

### 3.4. Три енума и четыре хардкода для «источника манифестов» — **желательно**

- **Что не так.** Одно и то же понятие «откуда берём мета-данные версий» выражено тремя типами: `ManifestType { Official, Prism }` (`instance/download/libs/mod.rs:22`), `ManifestTypes { MojangVersionManifest, PrismVersionManifest }` (`endpoint/versions.rs:20`), `MetaProviders { Mojang, Prism }` (`utils/unify/mod.rs:18`). URL-ы продублированы: `version_manifest_v2.json` — в `endpoint/versions.rs:53`, `manifest/mod.rs:3`, `utils/unify/mod.rs:26`; `meta.prismlauncher.org` — в `endpoint/versions.rs:56`, `utils/unify/mod.rs:27`, `instance/download/libs/parse/prism.rs:15`.
- **Почему проблема.** Смена URL или добавление третьего провайдера (Modrinth и т.п.) потребует правок в 4+ местах; три енума с разной семантикой имён (`Official` vs `Mojang` vs `MojangVersionManifest`) путают.
- **Как исправить.** Один enum `MetaProvider { Mojang, Prism }` в отдельном модуле (например, `src/meta/mod.rs` или расширенный `manifest/`), с методами `index_url()`, `version_url(uid, version)`. Остальные три енума заменить на него.

### 3.5. Две функции отправки WS-сообщений с одинаково сломанной обработкой ошибок — **желательно**

- **Что не так.** `WsMessageType::send` (`websocket/messages/mod.rs:24`) и `OperationWsMessage::send` (`instance/websocket/mod.rs:42`) делают одно и то же: `ws.send_json(&json!(self))`. Обе используют бессмысленный паттерн `map_err(|e| { ...; return Err(...) }).unwrap()` — то есть при ошибке отправки процесс падает по panic, хотя код выглядит как «обработка ошибки».
- **Почему проблема.** Дублирование + одинаковая мина: разрыв WS-соединения клиентом уронит операцию инициализации инстанса целиком.
- **Как исправить.** Оставить одну реализацию (`WsMessageType::send`), возвращать `Result` честно и обрабатывать/логировать на вызывающей стороне. `OperationWsMessage` должен пользоваться ею через свой `From<OperationWsMessage> for WsMessage`, который уже написан (`instance/websocket/mod.rs:33`).

### 3.6. Три реализации детекции OS/arch — **желательно**

Описано в §2.2: `construct_os_name` (живая, `libs/mod.rs:137`), `utils/system.rs` (сирота), `java/parse/arch.rs` (мертвец). Оставить одну — на базе `utils/system.rs`.

### 3.7. `sha1` + `sha1_smol` — **косметическое**

В `Cargo.toml` обе; в коде используется только `sha1` (`utils/download/mod.rs:5`). Удалить `sha1_smol`. Полный список неиспользуемых зависимостей — §8.

### 5.5. `root.rs` — устаревший модуль с пересекающейся ответственностью — **желательно**

- **Что не так.** `LauncherRoot::init_root` (`src/root.rs`) создаёт корневой каталог и `/libraries` по пути, присланному клиентом, возвращая строки вида `"Root directory initialized successfully"` как API-ответ. Инициализацию каталогов сделать методом этого владельца (`ensure_layout()`), эндпоинт `/init/root` либо удалить, либо свести к вызову `ensure_layout()`. `root.rs` удалить.

## 6. Системные архитектурные проблемы

### 6.1. Транспорт протащен в доменный слой — блокер разделения на библиотеку и сервер — **критично**

- **Что не так.** `EndpointRequest` (алиас `tide::Request<Arc<GlobalDataState>>`, объявлен в `main.rs:35`) и `WebSocketConnection` проходят сквозь все слои: `Instance::init(data, register, opts, req, ws)` (`instance/init.rs:19`), `Options::change(req, ...)` (`options/mod.rs:58`), `Overview::update(change, req, id)` (`pages/overview.rs:63`), `Settings::update(change, req, id)` (`pages/settings.rs:52`) — вплоть до функций, чья работа — один SQL-запрос.
- **Почему проблема.**
    - **Блокирует запланированный сплит.** Ядро планируется разделить на feature «rust-библиотека» и feature «веб-сервер». Пока домен принимает `tide::Request`/`WebSocketConnection`, библиотечная сборка без tide не соберётся в принципе: `Instance`, `Options`, страницы options зависят от транспорта на уровне сигнатур. Отвязка домена — обязательное предусловие сплита, а не гигиена.
    - Домен нельзя протестировать без поднятого tide-стека — поэтому тестов на `Options::change`-цепочку и нет (существующие тесты в `options/tests.rs` покрывают только `ChangeRequestBuilder::build`, где `req` не нужен).
    - Сигнатуры врут: `Overview::update` из `req` берёт только `req.state().static_data.db` и `req.state()`.
- **Как исправить.** Правило: хендлеры в `endpoint/` распаковывают запрос и передают внутрь только то, что нужно (`&GlobalDataState`, `&Database`, данные). Модуль `java` уже так устроен: `register_external` берёт `state.get_java_service()` и отдаёт ему готовую модель (`endpoint/java.rs:46-55`) — этот паттерн распространить на instance/options. Для WS-прогресса — см. §6.2. Целевое состояние: домен (будущая библиотека) не имеет ни одного импорта `tide`/`tide-websockets`/`http_types`.

### 6.1a. Подготовка к сплиту: `lib.rs` + cargo-features — **критично** (предусловие плана)

- **Что не так.** Сейчас это чисто бинарный crate: точка входа — `main.rs`, `lib.rs` нет, features в `Cargo.toml` не объявлены. Алиас `EndpointRequest` живёт в `main.rs` и импортируется доменом (`crate::EndpointRequest`) — то есть домен зависит от бинарной точки входа, это инверсия зависимости.
- **Почему проблема.** Задуманное разделение «библиотека + feature веб-сервера» требует, чтобы библиотечная часть существовала как самостоятельная compile-unit с осознанным публичным API. Пока всё в bin-crate, «библиотеки» просто нет.
- **Как исправить.** После выполнения §6.1:
    - завести `lib.rs` с доменными модулями (`instance`, `java`, `data`, `websocket::messages` как модель событий, `utils`);
    - `[features] server = ["dep:tide", "dep:tide-websockets", "dep:http-types"]`; `endpoint/` и сам HTTP-слой — за `#[cfg(feature = "server")]`;
    - `main.rs` — тонкий бинарь (`required-features = ["server"]` в `[[bin]]`), содержащий только маршруты и bootstrap;
    - публичную поверхность библиотеки (какие типы/сервисы видят нативные фронтенды) выбрать явно — см. §7.3, который из-за этого перестаёт быть косметикой.
      Порядок важен: сначала отвязка домена (§6.1), потом механический сплит — иначе фичи придётся резать по живым зависимостям.

### 6.2. Два параллельных механизма прогресса — **критично**

- **Что не так.** Прогресс инициализации инстанса ведётся дважды: (1) внутренний реестр `Tasks` с broadcast для `/debug/tasks/notif`; (2) `OperationWsMessage`, шлющий стадии в WS запроса. `Instance::init` на каждой стадии вручную обновляет оба (`instance/init.rs:57-68`, `116-122`, `166-172`, `208-214`), причём с `.unwrap()` на каждом `update_task`.
- **Почему проблема.** Это одна ответственность («сообщить о прогрессе операции»), реализованная двумя несинхронизированными путями. Стадии уже разъезжаются: WS получает `complete_stage(FetchManifest)`, а Tasks просто перещёлкивается на следующую стадию. Каждая новая операция (установка Java) должна будет повторить всю двойную бухгалтерию.
- **Как исправить.** Единый источник событий: операция пишет события прогресса в один объект (`OperationHandle`/`ProgressSink`), а подписчики — реестр Tasks и WS-соединение — получают их из broadcast-канала. Инфраструктура для этого уже наполовину есть (notifier в `Tasks`). Тогда `Instance::init` перестанет знать о `WebSocketConnection` вовсе, что заодно решает половину §6.1. С учётом планируемого сплита это ещё и требование библиотечного API: нативный rust-фронтенд должен подписываться на прогресс напрямую (channel/callback), без WS — значит, канал событий обязан жить в библиотеке, а WS-ретрансляция — быть тонким подписчиком за feature `server`.

### 6.3. Лайфтайм `'a` в глобальном состоянии — **критично**

- **Что не так.** WS-сообщение `Task<'a>` с полями `name: &'a str`, `message: Option<&'a str>` (`websocket/messages/task.rs:8`) используется как **хранимое состояние** в реестре `Tasks<'a>`. Из-за этого лайфтаймом заражены `GlobalAppData<'a>`, `GlobalDataState<'a>`, `EndpointRequest<'a>` и каждая функция, принимающая их.
- **Почему проблема.** (1) Сериализуемое сообщение протокола и доменная запись о задаче — разные вещи; связав их, нельзя добавить в задачу состояние, не попадающее в протокол. (2) Лайфтайм на глобальном состоянии — постоянный источник борьбы с borrow checker: он вынуждает `name: &'static str` на практике и не даёт формировать имена задач динамически («Initialize instance "Foo"»). (3) Каждая новая структура в state тянет `<'a>` дальше. (4) После сплита (§6.1a) `GlobalDataState` станет публичным типом библиотеки — лайфтайм в нём будет проблемой уже каждого нативного фронтенда, а не только этого репозитория.
- **Как исправить.** Хранимый тип — `TaskEntry { name: String, status, stage, progress, message: Option<String> }` без лайфтайма; протокольный `Task` собирать из него при отправке (или просто перевести `Task` на `String` — для сообщений, создаваемых десятками, а не миллионами, экономия на заимствовании ничего не даёт). После этого `GlobalDataState`, `EndpointRequest` и весь стек теряют `<'a>`.

### 6.4. Инконсистентный доступ к данным — **желательно**

- **Что не так.** Модуль `java` имеет слой хранения: trait `JavaStore` + `DbJavaStore` (`java/storage.rs`). Всё остальное ходит в БД напрямую из логики: сырые `sqlx::query!` в `libs/download.rs:33`, `libs/register.rs:22`, `assets/download.rs:25`, `assets/register.rs:11`, `pages/overview.rs`, `pages/settings.rs`, `instance/list.rs`, `utils/db/mod.rs`.
- **Почему проблема.** Два стандарта в одном проекте: новый код будут писать «как ближайший сосед», и разнобой закрепится. Инлайновый SQL в логике загрузки не мокается в тестах (в отличие от `JavaStore`, который уже `Arc<dyn ...>` и готов к подмене).
- **Как исправить.** Не обязательно заводить репозитории на всё немедленно, но выбрать конвенцию и зафиксировать её: per-domain store-trait (как `JavaStore`) для сущностей с нетривиальными операциями (libraries, assets, instances), и придерживаться её при следующем касании каждого модуля. Отдельно: SQL для libraries/assets, живущий в файлах `download.rs`, — не своё место даже внутри модуля (скачивание и хранение — разные обязанности).

### 6.5. Реестры и доменные модули организованы по двум разным конвенциям — **желательно**

- **Что не так.** `Instances` и `Tasks` живут в `data/registry/{instance,task}/`, а `JavaRegistry` — в `java/registry.rs`. При этом доменные операции над инстансами разбросаны: `instance/` (init, launch, options), `data/registry/instance/` (реестр + broadcast), `instance/list.rs` (загрузка из БД), `utils/db/` (регистрация).
- **Почему проблема.** Для одинаковых по роли сущностей два адреса: «реестр X» ищется то в `data/registry/X`, то в `X/registry.rs`. Это ровно тот случай «похожие сущности организованы по-разному без объективной причины», который затрудняет навигацию.
- **Как исправить.** Модуль `java` демонстрирует лучшую организацию — вертикальный срез: `model / error / service / storage / registry` в одном каталоге. Рекомендую целевую структуру:
    - `instance/` → добавить `service.rs` (текущие статические методы `Instance::*` без `req`/`ws`), `registry.rs` (переехавший `data/registry/instance`), `model.rs` (`InstanceDataRow`, `InitData`, `RunData`);
    - `task/` (или `operation/`) → реестр задач + прогресс (§6.2);
    - `data/` остаётся инфраструктурой: `db`, `config`, общий `Registry<K,V>` (§3.3).
      Плюсы: один паттерн для всех доменов, `data/` перестаёт зависеть от `instance/` (сейчас `data/registry/instance` импортирует `instance::list` — инверсия зависимости инфраструктуры от домена). Минусы: механический объём переезда. Учитывая, что ветка и так реорганизует полпроекта (git status показывает переезд `endpoints→endpoint`, `data/instance→data/registry/instance`), лучше довести до единой схемы сейчас, пока код маленький.

### 6.6. Ошибки: половина проекта на `Result<_, String>` — **желательно**

- **Что не так.** thiserror-енумы есть у db/config/instance/java/registry, но весь слой загрузки — `Result<_, String>`: `LibsData::sync_libs` (`libs/mod.rs:86`), `AssetsData::extract_manifest_assets`, `download_with_checksum` (`utils/download/mod.rs:54`), `get_assets_manifest`, `unify`, `maven::build_file_path`-окружение, `Natives::extract` (`launch/natives.rs:9`). Причём заведённые енумы `LibsSyncError` и `AssetSyncError` объявлены, но функции всё равно возвращают `String`/используют их частично.
- **Почему проблема.** Строковые ошибки не матчатся, теряют источник, склеиваются через `format!` в лесенки «Failed to X: Failed to Y: Failed to Z»; вызывающий код не может отличить сетевую ошибку от несовпадения SHA1.
- **Как исправить.** По одному error-enum на модуль (образец уже есть — `DBError`, `JavaError`), `#[from]` для прокидывания. Начать с `utils/download` (`DownloadError`), от него типизировать libs/assets.

### 6.7. Ключи реестра инстансов: `usize` против `i64` — **желательно**

`InstancesMap = HashMap<usize, ...>` (`data/registry/instance/mod.rs:9`), при том что id в БД и в `InstanceDataRow` — `i64`. Отсюда касты `instance_lock.id as usize` (`operations.rs:92`) и `instance_id as usize` (`pages/overview.rs:76`). Привести ключ к `i64` — касты и потенциальные несовпадения исчезнут.

### 6.8. `println!` как система логирования — **желательно**

Весь вывод — `println!`/`eprintln!`, включая отладочные дампы целых структур (`println!("{:#?}", result)` в `init.rs:135`, дамп аргументов запуска в `execute.rs:11`). Для «ядра», работающего фоновым процессом у пользователя, нужен `log`/`tracing` с уровнями — иначе нельзя ни выключить шум, ни собрать диагностику. Механическая замена, можно делать постепенно.

## 7. Структура директорий и модулей

### 7.1. Однофайловые каталоги с `mod.rs` против плоских файлов — **косметическое**

- **Что не так.** Смешение стилей без причины: `instance/paths/mod.rs`, `instance/websocket/mod.rs`, `utils/db/mod.rs`, `utils/metacache/mod.rs`, `data/db/mod.rs`, `utils/unify/mod.rs` — каталоги ради одного файла; рядом `instance/list.rs`, `instance/init.rs`, `java/*.rs` — плоские файлы.
- **Как исправить.** Конвенция: каталог — только когда есть ≥2 подфайла (как `instance/download/`, `websocket/messages/`). Остальное — плоские `paths.rs`, `db.rs`, `unify.rs`. Современный стиль Rust (2018+) вообще предпочитает `foo.rs` + `foo/` вместо `foo/mod.rs` — можно принять его целиком, но главное — единообразие.

### 7.2. `websocket/` — обёртка вокруг единственного подмодуля — **косметическое**

`src/websocket/mod.rs` содержит одну строку `pub mod messages;`. Либо поднять содержимое (`websocket/messages/*` → `websocket/*`), либо оставить как есть, если сюда переедет `OperationWsMessage` (§5.3) — тогда текущая структура оправдана. Рекомендую второе.

### 7.3. Непоследовательная видимость модулей — **желательно** (в связке с §6.1a)

В `main.rs:24-33`: `pub mod instance/java/root`, но `mod data/endpoint/manifest/utils/websocket`. Пока crate бинарный, `pub` не даёт ничего и это была бы косметика. Но с планом библиотечного feature видимость превращается в проектирование публичного API: при заведении `lib.rs` (§6.1a) нужно осознанно решить, что видят нативные фронтенды (сервисы, модели, типы событий), а что остаётся внутренним (`endpoint/`, storage-реализации, утилиты). Текущий случайный набор `pub` — плохая отправная точка для этого решения.

### 7.4. Маршруты API непоследовательны — **желательно, высокий приоритет**

`main.rs:51-83`: WS-эндпоинты то под `/ws/...` (`/ws/instance/init`), то нет (`/instance/options/sync`, `/debug/tasks/notif` — тоже WS); `/instance/download_versions` — POST с телом-выбором провайдера, `/instance/download_versions_unified` — GET; версии почему-то под `/instance/`, хотя к конкретному инстансу отношения не имеют; `/instance/:id/:page` перехватывает по шаблону и `/instance/options/...`-подобные пути.

Поскольку модульность лаунчера обеспечивается именно на границе API ядра, HTTP/WS-маршруты — это публичный контракт для всех не-rust фронтендов. Чем позже наводить порядок, тем дороже: после появления второго клиента любое переименование — breaking change. Предложение: `/ws/*` строго для WS; `/versions/*` для манифестов; `/instances/:id/*` для инстансов (множественное число, как таблица в БД).

### 7.5. Расположение тестов — **косметическое**

Два стиля: выделенные файлы (`instance/options/tests.rs`, `utils/download/tests.rs` через `#[cfg(test)] mod tests;`) и инлайновые `mod tests` (`utils/maven.rs:81`, `instance/launch/mod.rs:162`, `websocket/messages/mod.rs:73`). Оба валидны; стоит выбрать правило (например: инлайн до ~50 строк, дальше — файл) и придерживаться.

### 7.6. Тест как генератор биндингов — **информационно**

`export_bindings` (`websocket/messages/mod.rs:80`) — тест, который пишет файлы в `bindings/websocket`. Это стандартный приём ts-rs, оправдан. Единственный риск: биндинги обновляются только при запуске тестов; стоит зафиксировать это в README/CI, чтобы `bindings/` не разъезжался с кодом.

## 9. Что оправдано и менять не нужно

Чтобы аудит не выглядел как «переписать всё», фиксирую решения, которые считаю правильными:

- **`utils/download`: `BufferPool` + `Download<T: Downloadable>`** — аккуратная, законченная абстракция: пул буферов с guard-возвратом, потоковый SHA1, обработка редиректов, тесты на httpmock. Именно на ней стоит строить общий синхронизатор из §3.1.
- **Архитектура модуля `java`** (`model/error/service/storage/registry`, store за `Arc<dyn Trait>`) — образцовая для проекта; рекомендации §6 сводятся к «сделать остальным так же».
- **Типизированный WS-протокол + ts-rs** (`websocket/messages/*` → `bindings/`) — сильное решение: единый источник типов для ядра и веб-клиентов. В целевой архитектуре роль модуля даже вырастает: это общая модель событий — нативные rust-фронтенды потребляют эти типы напрямую из библиотеки, веб-клиенты — через ts-rs-биндинги.
- **`data/registry` как идея** (реестры в памяти + broadcast для live-обновлений клиентов) — оправдана; претензии только к дублированию (§3.3) и месту жительства (§6.5).
- **`Options`/`pages` с trait `ReadPage` и `*Fields`-патчами** (`COALESCE`-обновления, `deny_unknown_fields`, `skip_serializing_none`) — разумная схема частичных обновлений; после отвязки от `req` (§6.1) станет полноценной.
- **Миграции 0003/0004** (переименование и откат колонки) — выглядят как шум, но это корректная линейная история sqlx; переписывать применённые миграции нельзя, оставить как есть.
- **`getset` для геттеров** — вкусовщина, вреда нет; менять не предлагаю.
