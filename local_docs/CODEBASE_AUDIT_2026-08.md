# Аудит кодовой базы `sonata_launcher_core`

Дата: 2026-08-17. Ветка `next-gen`, рабочее дерево (почти всё в `src/` — untracked).
Объём: 79 файлов, 6806 строк Rust.

Предыдущие документы: `FULL_ARCHITECTURE_AUDIT.md` (2026-07-20, ветка `feature/java-manager`),
`NATIVE_IPC.md`. Расхождения с ними — разделы 5 и 6.

---

## 1. Исходное состояние

**Крейт компилируется.** `cargo check` — 0 ошибок, 21 предупреждение. Это большой сдвиг
относительно июльского аудита: миграция на новое поколение архитектуры в основном произошла.
Вертикальные срезы `java` / `instance` / `options` / `version` построены по одному образцу,
транспорт из домена вынут, лайфтайм из глобального состояния убран, два механизма прогресса
схлопнуты в один `EventBus`.

**Но крейт ничего не делает.** `main()` состоит из `tracing_subscriber::fmt::init()` и `Ok(())`;
`GlobalState::new` не вызывается («struct `GlobalState` is never constructed»). Из этого следуют
два практических вывода, важных для чтения всего остального:

1. **Дедукция мёртвого кода сейчас не работает.** `main.rs:1-4` объявляет `pub mod instance/java/
root/version` — для `pub`-модулей бинарного крейта rustc считает содержимое «экспортируемым» и
   не проверяет достижимость. Поэтому предупреждений мало. Если временно заменить `pub mod` на
   `mod`, компилятор выдаёт ~200 предупреждений «never used» — весь домен, включая `Syncer`,
   `LibsData`, `LaunchInfoBuilder`, `install`. Это не значит, что код лишний; это значит, что
   **компилятор сейчас не может отличить задел от мусора**, и мы лишились самого дешёвого
   инструмента поиска мёртвого кода. Лечится заведением `lib.rs` (раздел 7, шаг 3).
2. **Ничего из написанного не проверено в работе.** Полный путь `create → install → launch` не
   вызывался ни разу с момента рефакторинга. Баги из раздела 3 найдены чтением, а не прогоном, —
   и, скорее всего, это не все.

Отдельно: **`.sqlx` устарел.** `SQLX_OFFLINE=true cargo check` падает на четырёх запросах
`instance/options/storage.rs:76,103,129,150` — «no cached data for this query». Нужен
`cargo sqlx prepare`. Сейчас сборка проходит только потому, что `.env` подставляет `DATABASE_URL`
и макросы ходят в живую БД. В CI или на чужой машине сборки не будет.

## 3. Баги в живом коде

Отсортированы по тому, насколько тихо ломаются.

### 3.1. ✔️ URL под-манифестов Prism склеивается без разделителя — **ломает Fabric/Quilt/Forge**

`download/libs/parse/prism.rs:117`:

```rust
let base_url = self.provider.source().base_url();   // "https://meta.prismlauncher.org/v1"
let url = format!("{}{}/{}.json", base_url, uid, suggests);
```

`PrismSource::base_url()` (`version/provider/prism.rs:44`) возвращает строку **без** хвостового
слэша. Прежняя константа `META_BASE_URL` (`prism.rs:10`, ныне мёртвая) слэш имела. При переходе на
`base_url()` формат строки не поправили. Получается:

```
https://meta.prismlauncher.org/v1net.minecraft/1.20.1.json
```

Ветка `requires` — это и есть путь загрузки лоадеров и `net.minecraft` для Prism-провайдера,
который стоит провайдером по умолчанию (`config.rs:30`). Любой инстанс с непустым `requires` падает
с `ManifestMalformed`.

Правка: `format!("{}/{}/{}.json", …)`.

### 3.2. ✔️ Выбранный java-рантайм не используется при запуске

`launch/execute.rs:14`:

```rust
let output = Command::new("java").args(args).output().await.unwrap();
```

`LaunchInfo.java_bin_path: JavaRuntime` заполняется, но не читается никогда (предупреждение
компилятора «fields `java_bin_path` and `name` are never read»). Игра всегда стартует системной
`java` из `PATH`. Весь модуль `java` — детекция, регистрация, выбор в настройках инстанса — на
запуск не влияет.

Там же ещё две проблемы: `.unwrap()` роняет процесс, если `java` не найдена, а `.output()` ждёт
завершения игры и буферизует весь её вывод в память вместо `.spawn()`.

### 3.3. ✔️ События прогресса молча теряются

`bus/mod.rs:19`:

```rust
pub fn publish(&self, event: impl Into<CoreEvent>) {
    self.tx.try_broadcast(event.into());     // Result проигнорирован
}
```

Компилятор ругается: «unused `Result` that must be used». `async_broadcast` при заполненном канале
возвращает `Err(Full)`, при отсутствии активных получателей — `Err(Inactive)`. Ёмкость — 32
(`config.rs:22`), а `Syncer` шлёт событие **на каждый скачанный файл**: несколько тысяч на ассетах.
Медленный подписчик (или его отсутствие) — и прогресс просто исчезает, без следа в логах.

Это прямо противоречит посылке `NATIVE_IPC.md` §6 («нативный клиент получает `Event` как готовую
структуру»): сегодня он получит подмножество событий, размер которого зависит от скорости диска.

Варианты: `set_overflow(true)` (дропать старейшее, прогресс самовосстанавливается следующим
событием) — для прогресса это правильное поведение; но тогда `Finish` тоже может потеряться, так
что терминальные события лучше слать `broadcast().await`. Минимум — перестать глотать `Result`.

### 3.4. ✔️ `AssetsOutcome.total` считает только кэш

`download/assets/mod.rs:117`:

```rust
Ok(AssetsOutcome {
    total: outcome.cached.len(),              // ← без downloaded
    downloaded: outcome.downloaded.len(),
})
```

На чистой установке `total == 0`, `downloaded == 3500`. Должно быть
`outcome.cached.len() + outcome.downloaded.len()` (в `libs` аналогичное место сделано верно —
через `outcome.all()`).

### 3.5. ✔️/ `launch/traits.rs` не компилируется под macOS

```rust
let matched_traits = Vec::new();          // :15, без mut
...
#[cfg(target_os = "macos")]
matched_traits.push(StartupTraits::FirstThreadOnMacOS);   // :23
```

`mut` убрали по предупреждению компилятора на Linux, где `push` вырезается атрибутом `cfg`. На
macOS этот `push` включается и даёт E0596. Кросс-платформенный breakage, который не видно на
машине разработки.

Заодно: `extract` возвращает `Err(TraitsNotFound)`, когда в манифесте просто нет `+traits`. Это не
ошибка, а норма; вызывающий (`execute.rs:40`) печатает её в stdout на каждом запуске. Должен
возвращаться пустой `Vec`.

### 3.6. Генерация TypeScript-биндингов умерла, `bindings/` протух

В живом коде остался один `#[derive(TS)]` — на пустой структуре `StageError`. Ни одного
`#[ts(export)]`, ни теста `export_bindings`. При этом:

- `.cargo/config.toml` по-прежнему задаёт `TS_RS_EXPORT_DIR = "bindings"`;
- в `bindings/websocket/` лежат 32 `.ts`-файла, описывающих **предыдущий** протокол: `BaseMessage`,
  `WsMessage`, `Task`, `TaskStatus`, `ProgressUnit`, `InstanceFields`, `ExportTypes` — ни одного из
  этих типов в коде больше нет;
- четыре из них показаны в `git status` как изменённые — то есть их правили руками.

Июльский аудит (§9) называл ts-rs-контур одним из трёх сильных решений проекта. Сейчас его нет.
Если веб-клиент планируется — контур надо восстанавливать на новых типах (`OperationMessage`,
`ScanMessage`, `OptionUpdateMessage`, `PageView`, `Overview`, `Settings`) и переносить генерацию из
`#[test]` в `src/bin/export_bindings.rs`. Если нет — удалить `bindings/`, `ts-rs` и строку из
`.cargo/config.toml`, чтобы не выглядело работающим.

### 3.7. ✔️ `download_manifest` — три `.unwrap()` и склейка путей строками

`download/manifest.rs:33-45`:

```rust
let name_start_pos = url.rfind('/').unwrap();
let full_path = format!("{}{}", save_path.as_ref().display(), url[name_start_pos..].to_string());
let dir_last_pos = full_path.rfind('/').unwrap();
...
let mut index_file = File::create(&full_path).await.unwrap();
    .write_all(serde_json::to_string_pretty(&data).unwrap().as_bytes())
```

URL без `/` — паника. Нет прав на запись — паника (и это единственное место, где ошибка записи
манифеста не обёрнута в `WriteFailed`, хотя вариант ошибки существует). Плюс путь собирается
конкатенацией с `/` — на Windows не работает; `Path::join` решает и это, и оба `rfind`.

Та же болезнь в `utils/maven.rs:66` (`build_file_path` возвращает `String`, хардкодит `/`) и в
`libs/parse/prism.rs:153` (путь до `mainJar` собирается `format!`, минуя `build_maven_file_path`).
Корень один: `LibInfo.path` — `String`, а не `PathBuf`.

### 3.8. ✔️ `handle_simple_arg` режет строку по байтам

`launch/execute.rs:136`: `if &arg[..2] == "${"` — паника на аргументе короче двух байт и на
не-ASCII границе. `arg.starts_with("${")` делает то же самое безопасно.

### 3.9. `MetaProvider::Mojang => todo!()`

`version/provider/mod.rs:44`. Сейчас недостижимо, потому что `Config::init` жёстко ставит
`Prism`, а `instance.meta_provider` из БД нигде не парсится обратно в enum. Как только появится
выбор провайдера — паника в проде. Либо реализовать `MojangSource`, либо убрать вариант из enum до
реализации: несуществующий вариант лучше паникующего.

### 3.10. ✔️ `InstanceId` реализует `std::error::Error`

`instance/model.rs:6`:

```rust
#[derive(Debug, Clone, Copy, Hash, PartialEq, Eq, Error, Serialize, Deserialize, sqlx::Type)]
#[error("{0}")]
pub struct InstanceId(i64);
```

Это моя ошибка в `REFACTOR_OPTIONS_IMPL.md`: `Display` нужен для `#[error("… {0}")]` в
`InstanceError::NotFound`, но получен он через derive `Error`, который заодно объявляет
идентификатор ошибкой. `InstanceId` начинает подходить под `?`-конверсии и `Box<dyn Error>`, где
ему делать нечего. Заменить на явный `impl fmt::Display`.

## 4. Что подправить

### 4.1. Логирование

`main.rs:16` инициализирует `tracing_subscriber`, после чего **ни одной записи через `tracing` в
проекте нет**: ~30 мест `println!`/`eprintln!` в живом коде, включая отладочные дампы целых
структур — `launch/mod.rs:139` (`println!("{:#?}", self.game_args)`), `execute.rs:11`
(весь список аргументов), `natives.rs:10` (список путей), `utils/download/mod.rs:117,135`
(строка на каждый скачанный файл — тысячи строк на установку). Замена механическая, делается
постепенно, но подписчик уже стоит — сейчас он просто ничего не печатает.

### 4.2. `Result<_, String>` в оставшихся местах

Типизированы: `DbError`, `InstanceError`, `JavaError`, `VersionError`, `OptionsError`,
`LibsSyncError`, `AssetSyncError`, `SyncError`, `ManifestError`, `LaunchError`. Осталось:
`utils/download::download` и `download_with_checksum` (`mod.rs:16,54`), `Natives::extract`
(`natives.rs:9`), `root.rs`, `manifest/mod.rs` (оба под снос).

`download_with_checksum` — самое неприятное из оставшегося: `SyncError::DownloadsFailed` несёт
`first: String`, поэтому вызывающий не может отличить сетевой сбой от несовпадения SHA1 и,
например, не может решить «повторить» или «сдаться». Нужен `DownloadError { Http, Io, ChecksumMismatch { expected, got }, TooManyRedirects }`.

### 4.3. Три способа узнать ОС — по-прежнему

`construct_os_name()` (`libs/mod.rs:158`, живая), `utils/system.rs` (сирота), `java/parse/arch.rs`
(мертвец). §2.2/§3.6 июльского аудита не закрыт. Решение то же: одна реализация на
`(OsType, ArchType)` enum-ах, `construct_os_name` поверх неё маппингом в строку формата Mojang.
Пока скачивания Java нет, дешевле снести обе лишние копии и вернуться к вопросу вместе с ней.

### 4.4. Мелочи

- ✔️ `InstancePaths::navites()` (`paths/mod.rs:22`) — опечатка в публичном имени, вызывается из
  `init.rs:43`. Новая, июльский аудит её не застал.
- `VersionKind` приватен, но торчит в `pub VersionSummary::kind` — предупреждение
  «type is more private than the item». Сделать `pub`.
- `PrismSource::index_url()` дублирует `base_url()` литералом; вывести из него.
- Однофайловые каталоги: `instance/paths/mod.rs`, `data/db/mod.rs`, `bus/mod.rs`,
  `data/registry/mod.rs`, `manifest/mod.rs`. §7.1, косметика.
- `OptionsStore::overview/settings` используют `fetch_one` → несуществующий инстанс даёт
  `DbError::NotFound("Row not found")` вместо `OptionsError::InstanceNotFound(id)`.
  `fetch_optional` + `ok_or`.
- В `sync.rs` нет тестов, хотя план (`REFACTOR_DOWNLOAD_IMPL.md`) их описывал: полный кэш даёт
  100% с первого события, дубликаты качаются один раз, частичный провал регистрирует успешные,
  прогресс монотонен. Это единственный по-настоящему общий кусок логики в проекте — он их стоит.
- `Regex::new(…).unwrap()` в `maven::coord_to_path:27` компилируется при каждом вызове;
  `std::sync::LazyLock`.

## 6. Расхождения с `NATIVE_IPC.md`

Здесь расхождений больше, и они содержательнее: документ писался до рефакторинга и описывает
кодовую базу, которой уже нет.

### 6.1. Шаги 1–2 плана миграции (§8) выполнены

«Ввести шину событий, убрать `&WebSocketConnection` из `Instance::init`, убрать лайфтайм `'a` и
`tide`-типы из `Core`» — сделано: `EventBus` + `CoreEvent`, `install()` принимает
`&OperationHandle`, `GlobalState` без лайфтайма. Описания текущего состояния в §1 («хендлеры
принимают `EndpointRequest`, `Instance::init` шлёт прогресс сам») и §6 («прогресс идёт двумя
параллельными путями») устарели целиком.

### 6.2. `Command`/`Response`-enum противоречит тому, что построено — и, по-моему, проиграл заслуженно

`NATIVE_IPC.md` §5 предлагает единой точкой входа в ядро:

```rust
impl Core {
    pub async fn execute(&self, cmd: Command) -> Response;
    pub fn subscribe(&self) -> impl Stream<Item = Event>;
}
```

Построено другое: типизированные сервисы (`InstanceService`, `OptionsService`, `JavaService`,
`VersionCatalog`) с обычными async-методами и своими error-енумами, плюс `EventBus`. Половина §5
уже есть — это и есть «слой API ядра, не знающий про транспорт» из §1. Не хватает только
`Command`-обёртки.

И её, на мой взгляд, добавлять не надо — по крайней мере в ядро. Аргументы:

- `Command`/`Response` схлопывают все ошибки в один `Response::Error(CoreError)`. Сейчас
  `patch_settings` возвращает `OptionsError::JavaRuntimeNotFound(id)`, а `rename` —
  `OptionsError::NameTaken`; после схлопывания нативный клиент на Rust получит то же самое, что
  веб-клиент получает из JSON, — то есть потеряет ровно то преимущество, ради которого §2 вариант A
  и затевался.
- Диспетчеризация по enum-у — это нужда транспорта: чтобы разобрать кадр из сокета, нужен тег.
  Ин-процессному клиенту тег не нужен, он вызывает метод. Значит, `Command` — тип **адаптера**, а не
  ядра, и жить он должен рядом с IPC/HTTP-кодом, вместе с `match cmd { … }`, который зовёт сервисы.
- Иначе каждый новый метод сервиса придётся заводить трижды: метод, вариант `Command`, вариант
  `Response`.

Предложение: зафиксировать в `NATIVE_IPC.md`, что роль «слоя API» играют сервисы, а
`Command`/`Response` — деталь адаптера. Тогда §5 остаётся верным по духу и перестаёт конфликтовать с
кодом.

### 6.3. Посылка §6 («сотни событий прогресса без парсинга JSON») ломается о баг 3.3

Шина есть, но `publish` игнорирует `Err(Full)` при ёмкости 32. Прежде чем строить на ней IPC,
нужно решить политику переполнения. Это же место, кстати, определяет, можно ли вообще обещать
нативному клиенту «прогресс-бар без потерь».

### 6.4. §7 «ts-rs продолжает генерировать типы из тех же `Command`/`Response`/`Event`» — неверно

Генерации нет (3.6). Если веб-путь сохраняется, это предусловие, а не следствие.

### 6.5. Два несовместимых способа сплита

- `NATIVE_IPC.md` §8 шаг 4: «вынести `Core` в **отдельный крейт** `launcher-core`, демон —
  `src/bin/daemon.rs`».
- `FULL_ARCHITECTURE_AUDIT.md` §6.1a и записанное решение по проекту: **один крейт, два
  cargo-feature** (библиотека / `server`).

Разные вещи. Отдельный крейт (или workspace из двух) даёт настоящую границу: библиотека физически
не может импортировать транспорт, и это проверяет `cargo`, а не дисциплина. Feature-флаги дешевле,
но `#[cfg(feature = "server")]` расползается по файлам, и «библиотечная сборка» ломается ровно
тогда, когда кто-то забыл атрибут.

Учитывая, что домен уже развязан, а от `tide` осталась одна нить импортов `async_trait` (5.1),
цена разделения на два крейта сейчас минимальна — и дальше будет только расти. Рекомендую workspace:
`core/` (библиотека) + `server/` (tide/axum-адаптер, зависит от `core`). Но это решение за вами;
главное — выбрать одно и поправить оба документа, потому что сейчас они предписывают разное.

### 6.6. §8 шаг 5: `tide`/`surf`/`async-std` → `tokio`/`axum`/`reqwest`

Не сделано, и это самое дорогое из оставшегося. Аргумент документа (async-std не поддерживается)
за месяц не ослаб. Затрагивает: `sqlx` (фича `runtime-async-std` → `runtime-tokio`), весь
`utils/download` (surf → reqwest), `async_std::task::spawn` в `sync.rs`, `async_std::process::Command`
в `launch/execute.rs` и `java/utils.rs`, `async_std::fs` в четырёх местах, `#[async_std::main]`.

Порядок относительно сплита имеет значение. Если сначала сплит, миграцию рантайма придётся делать в
двух крейтах сразу. Если сначала рантайм — сплит потом чисто механический. Я бы делал рантайм
первым.

### 6.7. `Command::InitRoot { path }` в §5

Противоречит §5.5 июльского аудита и разделу 2.2 этого: `root.rs` под снос, раскладку определяет
`LauncherPaths` от `Config`, клиент путь не присылает. Убрать из списка команд.

## 7. Порядок действий

Первые четыре шага дёшевы и снимают шум, мешающий всему остальному.

1. **Закоммитить как есть.** Весь `src/` untracked; следующий шаг необратим без этого.
2. **`cargo sqlx prepare`** — `.sqlx` не покрывает четыре запроса `options/storage.rs`, офлайн-сборки
   нет.
3. **Удалить шесть осиротевших каталогов** (2.1) — минус 1649 строк, минус ложные результаты грепа.
   Заодно `root.rs`, `manifest/mod.rs`, мёртвые функции из 2.2 и закомментированные блоки из 2.4.
4. **`tide::utils::async_trait` → `async-trait`** в шести файлах; выкинуть 12 неиспользуемых
   зависимостей (2.3). После этого `tide` остаётся только в сигнатуре `main`.
5. **Починить баги 3.1–3.5** — URL Prism, java-рантайм при запуске, потеря событий, `AssetsOutcome.total`,
   `mut` в `traits.rs`. Первые два ломают основной сценарий продукта.
6. **Завести `lib.rs`** и убрать `pub` с модулей в бинаре. Это возвращает работающий `dead_code` —
   после чего оставшийся мусор компилятор покажет сам, и раздел 2 этого документа больше не
   понадобится в ручном виде.
7. **Собрать `main()` обратно** — хотя бы `GlobalState::new()` + один сценарий
   `create → install → launch` под `#[async_std::test]` или временным CLI-аргументом. Пока путь ни
   разу не прогонялся, любой список багов остаётся списком гипотез.
8. **Решить два вопроса из раздела 6** и синхронизировать документы: (а) крейты или features,
   (б) остаёмся на async-std или мигрируем на tokio. Второй лучше делать до первого.
9. **Определиться с веб-путём.** Восстанавливать ts-rs-контур на новых типах — или удалить
   `bindings/`, `ts-rs` и `TS_RS_EXPORT_DIR`. Текущее состояние — худшее из трёх: контура нет, а
   артефакты лежат и выглядят живыми.

Дальше — `tracing` вместо `println!` (4.1), типизация `DownloadError` (4.2), тесты `Syncer` (4.4).
