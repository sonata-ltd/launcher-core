# Коммуникация ядра с нативным клиентом: как убрать оверхед веб-сервера, сохранив единую кодовую базу

> Контекст: сейчас ядро — это локальный демон на `tide` (HTTP + WebSocket на `127.0.0.1:8080`),
> общение с клиентом идёт через JSON по сети (сериализация/десериализация на каждый запрос и на
> каждое событие прогресса). Изначально клиент задумывался как веб-интерфейс. Теперь пишется
> **нативный** клиент, и для него веб-сервер + JSON — лишний оверхед.
>
> Задача этого документа: предложить подход, который (1) даёт нативному клиенту минимальный
> оверхед, (2) сохраняет возможность обслуживать веб-клиенты и другие клиенты из **одной** кодовой
> базы ядра.

---

## 1. Ключевая идея: разделить «ядро-библиотеку» и «транспортные адаптеры»

Главная причина текущего оверхеда — **транспорт вшит в логику**. Хендлеры принимают
`EndpointRequest` (тип `tide`), возвращают `tide::Response`, вручную гоняют JSON и `WebSocketConnection`
прямо в бизнес-коде (`Instance::init` принимает `&WebSocketConnection` и шлёт прогресс сам).
Из-за этого «убрать веб-сервер» = «переписать пол-ядра».

Решение — три слоя:

```
┌──────────────────────────────────────────────────────────────┐
│  Транспортные адаптеры (тонкие, взаимозаменяемые)              │
│  ┌───────────────┐ ┌───────────────┐ ┌────────────────────┐  │
│  │ In-process /  │ │ IPC-сокет     │ │ HTTP + WebSocket    │  │
│  │ FFI (натив)   │ │ (UDS/pipe)    │ │ (веб-клиенты)       │  │
│  └───────┬───────┘ └───────┬───────┘ └─────────┬──────────┘  │
├──────────┼─────────────────┼───────────────────┼─────────────┤
│          ▼                 ▼                   ▼               │
│  Слой API ядра: async fn'ы, принимают типизированные          │
│  Command/Query, возвращают Result<T>, а прогресс отдают        │
│  через канал событий (Stream<Event>). НЕ знают про транспорт. │
├──────────────────────────────────────────────────────────────┤
│  Домен: instances, java, downloads, db, manifests…            │
└──────────────────────────────────────────────────────────────┘
```

Смысл: **бизнес-логика ничего не знает о транспорте**. Она оперирует типизированными
командами/событиями. Транспорт — сменный «чехол». Нативный клиент подключается напрямую (без
сериализации), веб-клиент — через тонкий HTTP/WS-адаптер (с сериализацией), и оба используют
один и тот же слой API.

Это, по сути, гексагональная архитектура (порты и адаптеры). После неё вопрос «gRPC или UDS или
FFI» становится вопросом выбора **одного адаптера**, а не переписывания ядра.

---

## 2. Что конкретно значит «нативный клиент» — три уровня близости

Прежде чем выбирать протокол, надо определить, **как именно** нативный клиент соседствует с ядром.
От этого зависит, сколько оверхеда вообще можно убрать.

### Вариант A. Ядро как библиотека внутри процесса клиента (нулевой оверхед)

Нативный клиент (например, на Rust — egui/iced/Slint/Tauri-без-webview, или на C++/Qt через FFI)
**линкует ядро как крейт** и вызывает его функции напрямую.

- **Оверхед сериализации: ноль.** Передаются Rust-структуры по значению/ссылке, никакого JSON.
- **Оверхед IPC: ноль.** Нет сокетов, нет копирования через ядро ОС.
- Прогресс долгих операций — через `async` `Stream`/`tokio::sync::broadcast`/канал, клиент просто
  подписывается на поток событий и получает **готовые Rust-значения**.

Это идеал для «полностью нативного» клиента и то, к чему стоит стремиться, если клиент тоже на Rust.

**Если клиент не на Rust** — ядро компилируется в `cdylib` и экспонирует C-ABI (FFI). Тогда:
- Для C/C++/Qt — прямые `extern "C"` функции.
- Для языков с GC (C#, Kotlin/JVM, Swift, Dart/Flutter) — тонкая FFI-граница. Здесь на границе
  всё же нужна сериализация в байты, но её можно сделать дешёвой (см. §4, forматы), и это всё
  равно на порядок дешевле HTTP+JSON поверх TCP.

### Вариант B. Ядро — отдельный процесс, клиент рядом (низкий оверхед)

Ядро остаётся демоном, но общение идёт не по TCP+HTTP, а по **локальному IPC**: Unix domain socket
(Linux/macOS) или Named Pipe (Windows). Через абстракцию это один и тот же код (крейт
`interprocess` или `tokio`'овые `UnixListener`/`NamedPipe`).

- **Нет сетевого стека** (нет TCP/IP, нет HTTP-парсинга, нет CORS/DNS-rebinding-рисков).
- UDS примерно **на порядок быстрее** локального gRPC/HTTP по латентности (см. бенчмарки ниже).
- Сериализация остаётся (процессы не делят память), но формат можно взять компактный бинарный.
- Плюс безопасность: права на сокет-файл/пайп ограничиваются текущим пользователем — чужой
  процесс/браузер не достучится (в отличие от открытого TCP-порта).

Это лучший баланс, если нужна изоляция «ядро как сервис» (обновляется отдельно, переживает
перезапуск UI, один ядро — несколько окон/клиентов).

### Вариант C. Оставить HTTP/WS, но только для веб/удалённых клиентов

Никуда не убираем — это просто **ещё один адаптер** поверх того же слоя API, включаемый по фиче-флагу
`--features http-transport`. Нативный клиент его не собирает и не платит за него.

**Рекомендация:** проектировать под **A или B как основной путь нативного клиента**, C — держать
опциональным адаптером для веба. Если клиент на Rust — цельтесь в A (in-process), с возможностью
собрать B (IPC-демон) той же кодовой базой. Если клиент на другом языке — B (IPC) как основной,
FFI (A) как опция для максимальной производительности.

## 3. Почему не «просто gRPC/protobuf вместо HTTP»

gRPC — резонный кандидат «единого протокола для всех», но для локального нативного клиента он
**не убирает главный оверхед**, а лишь меняет его форму:

- gRPC работает поверх HTTP/2 (тот же tokio + hyper/tonic-стек). Для **локального** IPC он
  примерно **в 10 раз медленнее** блокирующего I/O через Unix domain socket; типичная задержка
  унарного вызова ~100 µs
  ([F. Werner, gRPC for local IPC](https://www.mpi-hd.mpg.de/personalhomes/fwerner/research/2021/09/grpc-for-ipc/)).
- Для нативного in-process клиента (вариант A) gRPC — это **лишний** сетевой слой там, где можно
  вызвать функцию напрямую.
- Плюсы gRPC (строгая схема, кодогенерация клиентов на многих языках, стриминг) реальны, но их
  можно получить дешевле: схему и кодоген даёт `protobuf`/`prost` **без** транспорта gRPC —
  просто как формат сериализации поверх UDS.

Вывод: **protobuf/prost как формат — да, полезно; gRPC как транспорт — избыточно для локального
нативного клиента.** gRPC оправдан, только если появится сценарий «клиент на другой машине по
сети» или «много разноязычных клиентов, и удобство кодогена важнее 10× латентности». Тогда gRPC —
ещё один адаптер (вариант C-подобный), а не замена нативному пути.

Сравнение локальных транспортов (порядок величин, латентность унарного вызова):

| Транспорт | Относительная латентность | Сериализация | Когда брать |
|---|---|---|---|
| In-process вызов (A, Rust↔Rust) | ~нулевая | нет | клиент на Rust |
| FFI / C-ABI (A, другой язык) | очень низкая | дешёвый бинарь на границе | клиент на C++/C#/JVM/Swift |
| Unix socket / Named pipe (B) | низкая (~10× быстрее gRPC) | компактный бинарь | ядро-как-демон, изоляция |
| gRPC (HTTP/2) локально | ~100 µs, ×10 к UDS | protobuf | сеть / много языков |
| HTTP/1.1 + JSON (текущее) | высокая (парсинг+JSON) | JSON (дорого) | только веб-клиенты |

Источники: [gRPC for local IPC (mpi-hd)](https://www.mpi-hd.mpg.de/personalhomes/fwerner/research/2021/09/grpc-for-ipc/),
[servo/ipc-channel](https://github.com/servo/ipc-channel),
[interprocess (crates.io)](https://crates.io/crates/interprocess),
[The State of Async Rust (corrode.dev)](https://corrode.dev/blog/async/).

## 4. Формат сообщений на границе (там, где сериализация всё же нужна)

Для вариантов B и не-Rust-A нужен формат. JSON (текущий) — самый дорогой. Варианты по возрастанию
эффективности:

1. **JSON** — только для веб-адаптера (браузер его любит, DevTools читаемы). Оставить здесь.
2. **MessagePack** (`rmp-serde`) — «бинарный JSON», drop-in по `serde`, заметно компактнее и
   быстрее JSON, схема не нужна. **Лучший быстрый выигрыш**: меняется одна строка сериализатора,
   типы (`#[derive(Serialize, Deserialize)]`) те же. Хорош для IPC, где обе стороны на Rust или
   есть msgpack-библиотека.
3. **bincode** — максимально компактный/быстрый Rust↔Rust бинарный формат. Идеален для UDS
   между двумя Rust-процессами, но не кросс-язычный.
4. **protobuf/prost** или **FlatBuffers/Cap'n Proto** — если нужна кросс-язычная схема и кодоген
   клиентов. FlatBuffers/Cap'n Proto дают **zero-copy** чтение (не десериализуют всё в структуры),
   что снижает оверхед для больших сообщений (списки версий, манифесты). Ценой — эргономика хуже
   serde.

**Практичный выбор:**
- Rust↔Rust in-process (A): **никакого формата** — нативные значения.
- Rust↔Rust IPC (B): **bincode** или **MessagePack**.
- Кросс-язык (FFI/IPC): **MessagePack** (просто) или **protobuf** (строгая схема, кодоген).
- Веб (C): **JSON** как сейчас.

Важно: поскольку типы уже все выводят `serde::Serialize/Deserialize` и `ts-rs`, **выбор формата
становится параметром адаптера**, а не переписыванием моделей. Один и тот же `WsMessage` может
уходить в JSON веб-клиенту и в MessagePack — нативному.

## 5. Единый контракт: команды, запросы, события

Чтобы «одна кодовая база» работала, надо явно описать протокол как **типы Rust**, а не как набор
URL-роутов. Сейчас контракт размазан по роутам `main.rs` и разным структурам. Предлагается:

```rust
// Запросы клиента → ядро (то, что раньше было POST/WS-сообщениями)
pub enum Command {
    InitRoot { path: PathBuf },
    InstanceInit(InitData),
    InstanceRun(RunData),
    InstanceList,
    OptionGet { id: i64, page: Page },
    OptionChange(ChangeRequest),
    JavaRegisterExternal(NewJavaRuntime),
    JavaDetectProperties { exec_path: PathBuf },
    VersionsList(ManifestType),
    // …
}

// Немедленный ответ на команду
pub enum Response {
    Ok,
    Instance(InstanceView),
    Instances(Vec<InstanceView>),
    Page(PageResult),
    Java(JavaRuntime),
    Versions(Vec<UnifiedVersion>),
    Error(CoreError),
    // …
}

// Асинхронные события (прогресс, сканы, обновления) — то, что раньше слал WebSocket
pub enum Event {
    Operation(OperationMessage),
    Scan(ScanMessage),
    Task(TaskUpdate),
    OptionUpdate(OptionUpdateMessage),
}
```

И единая точка входа в ядро, **не зависящая от транспорта**:

```rust
pub struct Core { /* GlobalDataState без лайфтайма и без tide */ }

impl Core {
    /// Выполнить команду. Прогресс уходит в шину событий (см. ниже), а не в WebSocket.
    pub async fn execute(&self, cmd: Command) -> Response;

    /// Подписка на поток событий (замена «держим receiver живым»).
    pub fn subscribe(&self) -> impl Stream<Item = Event>;
}
```

Тогда транспортные адаптеры становятся тривиальными:

- **In-process (A):** клиент напрямую держит `Core`, зовёт `core.execute(cmd).await`, слушает
  `core.subscribe()`. Ноль сериализации.
- **IPC (B):** адаптер читает кадр из сокета → `bincode::deserialize::<Command>` → `core.execute`
  → `bincode::serialize(response)` → в сокет. Отдельная задача перекачивает `core.subscribe()` →
  кадры событий в сокет.
- **HTTP/WS (C):** роут → `serde_json::from_...::<Command>` → `core.execute` → JSON-ответ; WS-петля
  перекачивает `subscribe()` в JSON-фреймы. **Один раз** написанный адаптер обслуживает все
  веб-эндпоинты; больше не нужно по функции на роут.

Это заодно чинит ряд проблем из аудита: убирает `&WebSocketConnection` из бизнес-логики
(`Instance::init` больше не шлёт прогресс сам — он пишет `Event` в шину), убирает лайфтайм `'a`,
устраняет заглушки-хендлеры вроде `instance_options_sync`.

## 6. Прогресс долгих операций без привязки к соединению

Сейчас прогресс идёт двумя параллельными путями: внутренний `Tasks`-broadcast и прямая отправка
в `WebSocketConnection` через `OperationWsMessage`. Это дублирование и источник костылей
(`_receiver`, ручные `.unwrap()` при отправке).

Единый механизм: **одна шина событий** на `Core` (`tokio::sync::broadcast` для fan-out нескольким
подписчикам, либо `async_broadcast`, но с корректной обработкой отсутствия подписчиков). Логика
загрузки/установки просто публикует `Event::Operation(...)`; кто подписан (нативный клиент напрямую,
IPC-адаптер, WS-адаптер) — тот и получает. Транспорт решает, как сериализовать.

Плюс: нативный клиент (A) получает `Event` как **готовую структуру** — прогресс-бар обновляется без
парсинга JSON на каждый чих (а таких событий при скачивании сотен ассетов очень много — это
ощутимая часть текущего оверхеда).

## 7. Веб-клиенты из той же кодовой базы

«Единая кодовая база под остальные клиенты» сохраняется так:

- Слой `Core` + `Command`/`Response`/`Event` — общий для всех.
- Веб-адаптер (`features = ["http"]`) — тонкая обёртка (лучше на `axum`/`tokio`, т.к. `tide` мёртв,
  см. аудит §2.1): HTTP для унарных команд, один WebSocket для потока событий и/или для
  команд-по-WS. Сериализация — JSON.
- `ts-rs` продолжает генерировать TypeScript-типы из **тех же** `Command`/`Response`/`Event`, так
  что веб-клиент получает типобезопасный контракт автоматически. (Заодно чинится проблема
  «биндинги через `#[test]`» — генерация переезжает в отдельный бинарь/CI, см. аудит §7.)

Итог: добавить нативный клиент можно, **не трогая** веб-путь; добавить веб-функцию — она сразу
доступна нативному клиенту, потому что обе стороны говорят на `Command`/`Event`, а не на URL.

## 8. План миграции (инкрементально, без «переписать всё с нуля»)

Порядок такой, чтобы на каждом шаге проект оставался рабочим:

1. **Развязать бизнес-логику и транспорт.** Ввести `Command`/`Response`/`Event` и `Core::execute`/
   `subscribe`. Существующие `tide`-хендлеры переписать в тонкие обёртки, которые парсят вход →
   зовут `Core` → сериализуют выход. Прогресс перевести на шину событий, убрав `&WebSocketConnection`
   из `Instance::init`/загрузчиков. На этом шаге снаружи всё ещё HTTP/WS — ничего не сломалось.
2. **Убрать лайфтайм `'a` и `tide`-типы из `Core`** (owned `String` в `Task`, свой `Request`-агностик).
   Это развязывает ядро от `tide` окончательно.
3. **Добавить IPC-адаптер (вариант B)** на `tokio` + `interprocess` (UnixSocket/NamedPipe), формат —
   `bincode`/MessagePack. Нативный клиент переключается на него. HTTP/WS остаётся под фиче-флагом
   для веба.
4. **(Если клиент на Rust) добавить in-process путь (вариант A):** вынести `Core` в отдельный крейт
   `launcher-core`, который нативный клиент линкует напрямую. IPC-демон становится опциональной
   сборкой того же крейта (`src/bin/daemon.rs`).
5. **Заменить `tide`/`surf`/`async-std`** на `tokio` + `axum` (веб-адаптер) + `reqwest` (HTTP-клиент
   для Mojang/Prism). Это снимает стратегический риск мёртвых крейтов (см. аудит §2.1) и
   объединяет рантайм.
6. **Формат-параметризация:** сделать сериализатор адаптера настраиваемым (JSON для веба, bincode/
   msgpack для IPC), т.к. типы уже `serde`-совместимы.

Каждый шаг самодостаточен и оставляет сборку зелёной.

---

## 9. Итоговая рекомендация

- **Не заменять веб-сервер на gRPC.** Для локального нативного клиента gRPC — это тот же сетевой
  оверхед в новой обёртке (×10 к UDS локально). protobuf берите как **формат** (если нужен
  кросс-язык), но не как транспорт.
- **Целевая архитектура:** ядро-библиотека (`Core`) с транспортными адаптерами. Нативный клиент —
  in-process (Rust) или IPC/UDS (демон, любой язык); веб-клиент — тонкий HTTP/WS-адаптер поверх
  того же `Core`.
- **Быстрый выигрыш уже сейчас:** развязать логику и транспорт (шаг 1) + для нативного пути взять
  UDS + MessagePack/bincode вместо TCP + JSON. Это убирает сетевой стек и львиную долю
  сериализационного оверхеда, особенно на потоке событий прогресса, **не ломая** веб-путь.
- **Стратегически:** совместить эту развязку с уходом от `async-std`/`tide`/`surf` на `tokio`+`axum`,
  потому что фундамент под текущим сервером больше не поддерживается.

Такой подход даёт нативному клиенту околонулевой оверхед (вплоть до прямых вызовов функций),
сохраняет один и тот же домен и контракт для веба и других клиентов, и превращает выбор
«HTTP/gRPC/IPC/FFI» в выбор сменного адаптера, а не в переписывание ядра.
