# Детальный аудит ядра лаунчера (`sonata_launcher_core`)

> Дата анализа: 2026-07-19
> Ветка: `feature/java-manager`
> Объём кода: ~7000 строк Rust в `src/`, SQLite-хранилище, WebSocket/HTTP API на базе `tide`.

Документ разбит по областям: сначала критичные проблемы (то, что ломает сборку/тесты или
работает неверно прямо сейчас), затем архитектура, безопасность, производительность, нейминг,
структура проекта, генерация биндингов и «мелочи». В конце — сводная таблица приоритетов.

---

## 0. Резюме (TL;DR)

Ядро находится в состоянии активного прототипа: архитектурный костяк уже неплохой
(сервис-слой для Java, реестры с broadcast-уведомлениями, пул буферов для загрузок,
абстракция `Downloadable`, продуманная система сообщений WebSocket с генерацией TS-биндингов),
но поверх него много «времянок», хардкода путей под конкретную машину, паникующих `.unwrap()`
на путях ошибок и рассинхронизированных с кодом тестов и биндингов.

Главные болевые точки:

1. **7 из 24 тестов падают** (рассинхрон типа `id` в тестах опций и `todo!()` в билдере запуска).
2. **Фундамент на неподдерживаемых крейтах**: `async-std` официально прекращён (март 2025),
   `tide` и `surf` — фактически мертвы. Это стратегический риск №1.
3. **Хардкод абсолютных путей** конкретного пользователя (`/Users/quartix/...`) прямо в логике
   запуска и в `.cargo/config.toml` — на чужой машине не заработает.
4. **Запуск инстанса фактически не доделан** и паникует (`todo!("Implement default Java runtime")`),
   Java-раннтайм из БД игнорируется, вызывается системная `java`.
5. **Багованный classpath**: разделители `:` расставляются непоследовательно и хардкодятся
   под Unix — на Windows и в ряде путей classpath собирается в «слипшуюся» строку.
6. **Локальный веб-сервер без аутентификации + CORS `*`** — модель угроз для локального
   демона не проработана (DNS-rebinding/CSRF с любого сайта в браузере).

## 1. Критичные проблемы (ломают работу/сборку)

### 1.1. Падают 7 тестов из 24

`cargo test` → `test result: FAILED. 17 passed; 7 failed`.

**(а) Тесты опций (`src/instance/options/tests.rs`) рассинхронизированы с типом.**
В JSON тесты передают `"id": "8"` (строка), а `ChangeRequestBuilder.id: i64`
(`src/instance/options/mod.rs:74`). `serde_json` падает ещё до вызова `build()`:

```
Error("invalid type: string \"8\", expected i64", line: 3, column: 21)
```

При этом тест `parse_change_request_wrong_id` ожидает текст ошибки
`"Instance id is wrong: must be integer (i64), got \"wrongid\""` — такого варианта ошибки
в коде вообще нет (`InstanceError::WrongId` определён, но нигде не конструируется). То есть
тесты писались под другую (более раннюю или планируемую) реализацию, где `id` парсился
кастомно из строки. Нужно решить: либо `id` в API — строка с ручным парсингом (тогда вернуть
логику и `WrongId`), либо число (тогда переписать тесты). Рекомендуется строка на входе +
явная валидация, т.к. фронтенд-JSON часто присылает id строкой.

**(б) `builder_default_empty` (`src/instance/launch/mod.rs:166`) паникует.**
`LaunchInfoBuilder::build()` содержит `todo!("Implement default Java runtime")`
(`mod.rs:147`) — если `preferred_java` не задан, билдер паникует. Тест строит пустой билдер и
падает. Это не «тест плохой», это индикатор того, что путь «запуск без явно выбранной Java»
не реализован вообще.

### 1.2. Запуск инстанса не доведён до конца

- `LaunchInfoBuilder::build()` паникует без Java-раннтайма (см. выше). При этом реальный поток
  `Instance::init` **никогда не вызывает** `set_preferred_java_runtime`, значит любой реальный
  запуск через `run_instance_ws` тоже упрётся в `todo!()`.
- `launch_instance` (`src/instance/launch/execute.rs:14`) запускает **системную `java`**
  (`Command::new("java")`), полностью игнорируя `LaunchInfo.java_bin_path` (тип `JavaRuntime`,
  который специально хранится). Весь модуль Java-реестра/сервиса пока не подключён к запуску.
- **Хардкод пути к нативам**: `execute.rs:49`
  `PathBuf::from("/Users/quartix/.sonata/instances/1.5.2/natives")` — прибитый путь конкретной
  машины и конкретной версии. На любой другой машине/версии натива распакуются не туда.
- JVM-аргументы `-Xms512M`/`-Xmx4096M` захардкожены (`execute.rs:26`), хотя есть страница
  Settings, которая логически должна ими управлять.
- Игровые аргументы (`--username`, токены и т.д.) закомментированы; аккаунты/сессии
  не реализованы — запускается «пустой» Minecraft.
- `Instance::run` (`src/instance/mod.rs:115`) при каждом запуске заново вызывает `init(...)`,
  то есть **повторно скачивает манифест/либы/ассеты** вместо чтения уже установленного инстанса
  из БД. Установка и запуск не разделены.

### 1.3. Баг сборки classpath

`SyncResult.classpaths` собирается из нескольких источников с ручной расстановкой разделителей,
и это делается непоследовательно:

- `add_to_classpaths` (`libs/download.rs:107`) добавляет `:` перед элементом, **кроме первого**.
- А `register_libs` (`libs/register.rs:38`) кладёт `item.path.clone()` **вообще без разделителя**.
- В `parse/prism.rs:140` разделитель вставляется ещё и в начало под-результата
  (`result.classpaths[0].insert(0, ':')`).
- Финальная сборка `LaunchInfoBuilder::build()` (`launch/mod.rs:134`) просто конкатенирует всё
  через `push_str` **без разделителя**.

Итог: реальный classpath из свежескачанных библиотек склеивается в одну строку без `:` и Java
его не разберёт. Разделитель к тому же **хардкодится как `:`** — на Windows нужен `;`
(правильно: `std::path::MAIN_SEPARATOR`-аналога нет для classpath, но есть соглашение
`;` на Windows / `:` на Unix; лучше собирать `Vec<PathBuf>` и джойнить через `env::join_paths`).

**Рекомендация:** хранить classpath как `Vec<PathBuf>` до самого конца и один раз собирать
через `std::env::join_paths(...)` — она сама подставит правильный разделитель ОС и корректно
экранирует.

### 1.4. `add_task` теряет данные задачи

`src/data/registry/task/operations.rs:58`:

```rust
let current_task = {
    task.lock().await;   // <-- точка с запятой: блок возвращает ()
};
```

Из-за `;` внутри блока `current_task` имеет тип `()`, и дальше в payload уходит
`"data": null` вместо самой задачи (`payload = json!({ "task": { "id", "data": current_task }})`).
Клиент при добавлении задачи получает пустые данные. Должно быть
`let current_task = task.lock().await; ... &*current_task`.

### 1.5. Паникующие `.unwrap()` на путях ошибок в хендлерах

Локальный демон не должен падать от «плохого» ввода, но сейчас падает:

- `detect_runtime_properties` (`endpoint/java.rs:60`): `detect_properties(...).await.unwrap()` —
  любой сбой запуска `java` (нет файла, не исполняемый) роняет обработку запроса.
- `WsMessageType::send` (`websocket/messages/mod.rs:24-34`): конструкция
  `.map_err(|e| { ...; return Err(...) }).unwrap()` **всегда паникует при ошибке отправки**
  (map_err возвращает `Err`, затем `.unwrap()` на нём). Логика самопротиворечива:
  функция возвращает `Result`, но фактически паникует вместо возврата `Err`.
- `OperationWsMessage::send` (`instance/websocket/mod.rs:42-55`) — та же схема с `.unwrap()`.
- `init_instances_list` (`data/registry/instance/operations.rs:26`): `.unwrap()` на загрузке
  всех инстансов из БД при старте — битая БД = падение всего процесса на старте.
- `download_manifest` (`instance/download/manifest.rs:27-34`): `url.rfind('/').unwrap()`,
  `File::create(...).unwrap()`, `write_all(...).unwrap()`, `to_string(...).unwrap()` — URL без
  `/` или ошибка записи на диск роняют процесс.
- `get_assets_manifest` (`manifest.rs:55`): `asset_index["id"].as_str().unwrap()`.
- `parse_manifest_official` (`libs/parse/prism.rs` и `official`): `self.manifest["id"].as_str().unwrap()`,
  `downloads["client"]["sha1"].as_str().unwrap()`.

Все они завязаны на структуру внешнего JSON от Mojang/Prism — при малейшем изменении формата
ядро упадёт целиком, а не вернёт понятную ошибку клиенту.

### 1.6. Рекурсивно-опасный `AssetInfo::get_hash`

`instance/download/assets/mod.rs`: у `AssetInfo` есть **и** inherent-метод `get_hash` (стр. 110),
**и** реализация trait-метода `Downloadable::get_hash`, которая вызывает `self.get_hash()`
(стр. 41-43). Сейчас спасает только правило Rust «inherent важнее trait», поэтому вызов уходит
в inherent-метод и рекурсии нет. Но это хрупко: любой рефакторинг (переименование, перенос
inherent-метода в трейт) превратит это в бесконечную рекурсию/переполнение стека. Метод должен
просто возвращать `&self.hash`, как в `LibInfo`.

## 2. Архитектура и стратегические риски

### 2.1. Весь стек построен на прекращённых крейтах

`Cargo.toml` завязан на:

- `tide = 0.16` — веб-фреймворк, **последний релиз 2021**, разработка остановлена.
- `async-std = 1.13` — рантайм, **официально прекращён 1 марта 2025**
  (сопровождающие рекомендуют миграцию на `smol`).
- `surf = 2.3` — HTTP-клиент поверх async-std, тоже фактически заброшен.
- `tide-websockets` подтянут **из личного git-форка** (`github.com/Qeatrix/tide-websockets`) —
  bus-factor = 1, невоспроизводимая сборка при недоступности форка, нет версионирования.
- `http-types = 2.12` — общий тип для tide/surf, тоже часть мёртвой экосистемы.

Это не «устаревшие версии», а **тупиковая ветка экосистемы**. Пока `feature/java-manager`
пишет нативный клиент — это идеальный момент вырезать tide/surf/async-std. См. отдельный
документ `NATIVE_IPC.md` — там предложен переход на `tokio` + `axum` (или полностью на IPC),
где HTTP/WS остаётся только опциональным адаптером для веб-клиентов.

Источники по статусу: [async-std deprecation (Rust Internals)](https://internals.rust-lang.org/t/async-std-deprecation/23395),
[async-std [unmaintained] (lib.rs)](https://lib.rs/crates/async-std),
[The State of Async Rust: Runtimes (corrode.dev)](https://corrode.dev/blog/async/).

### 2.2. «Стрингли-типизированный» слой манифестов

Практически весь разбор манифестов Mojang/Prism идёт через `serde_json::Value` и индексирование
строковыми ключами (`manifest["downloads"]["artifact"]["path"].as_str()`), например
`libs/parse/prism.rs`, `libs/parse/mod.rs`, `download/manifest.rs`, `launch/execute.rs`.

Проблемы:
- Нет схемы — ошибки формата ловятся в рантайме, часто через `.unwrap()`.
- Дублирование однотипного «достань url/sha1/path» в 4-5 местах с копипастой.
- `parse_manifest_official` и `parse_manifest_prism` содержат почти одинаковую логику правил ОС,
  разъехавшуюся в деталях (в official — свой разбор `rules`, в prism — функция `rules_applies`).

**Рекомендация:** описать типизированные структуры (`#[derive(Deserialize)]`) для манифестов
версии, ассетов, prism-меты и парсить в них. Это уберёт большую часть `.unwrap()` и копипаст,
и даст единое место для правил ОС/арки.

### 2.3. Повсеместные лайфтаймы `<'a>` там, где нужны owned-данные

`GlobalDataState<'a>`, `GlobalAppData<'a>`, `Tasks<'a>`, `Task<'a>` тянут лайфтайм только потому,
что `Task` хранит `name: &'a str` и `message: Option<&'a str>` (`websocket/messages/task.rs:8-17`).
Из-за одного `&str` лайфтайм протекает через всё глобальное состояние, `EndpointRequest<'a>`,
сигнатуры почти всех методов. Для долгоживущих задач в `HashMap` заимствованные строки —
антипаттерн (задача переживёт источник строки). Должно быть `name: String`, `message: Option<String>`,
после чего `'a` исчезает из десятков сигнатур и код резко упрощается.

### 2.4. Хрупкий паттерн «держим receiver живым»

В `Tasks` и `Instances` лежит поле `_receiver`/`_reciever: Arc<Mutex<Receiver<...>>>` с комментарием
«Add receiver to structure to let websocket connection stay alive». Это обход того, что
`async-broadcast` закрывает канал, когда исчезает последний Receiver. Хранить «фиктивный»
приёмник в состоянии — рабочий, но неявный костыль. Чище — использовать канал/шину, который
не закрывается при отсутствии подписчиков (или явно документировать инвариант и не прятать его
под `_`).

### 2.5. Идентификаторы задач переиспользуются и ломаются

`add_task` (`task/operations.rs:55`): `let task_id = data.len() + 1;`. При удалении задач из
`HashMap` длина уменьшается, и следующая задача получит **уже занятый** id → коллизия/перезапись.
Плюс `tasks_map` хранит `Weak<Mutex<Task>>`, а `update_task` удаляет протухшие записи «лениво»,
из-за чего `data.len()` вообще не отражает реальный максимум id. Нужен монотонный счётчик
(`AtomicU64`) или UUID.

### 2.6. `update_instance_name` / `add_instance` — семантика и «тихие» ветки

- `add_instance` (`registry/instance/operations.rs:84`) при отсутствии имени инстанса делает
  `return Ok(())` **до** вставки в map? Нет — вставка выше, но broadcast пропускается. При этом
  `get_all_instances_json` и `add_instance` полностью **пропускают инстансы без overview-имени**
  (`continue`/ранний return). Инстанс, у которого ещё не создана строка overview, станет
  «невидимым» для клиента. Хрупкая связка «инстанс виден, только если есть name».
- `update_instance_name` при не найденном id возвращает `GlobalAppDataError::TaskNotFound(id)` —
  ошибка **про задачу** в операции **про инстанс**. Нужен отдельный `InstanceNotFound`.
- В обоих методах `BaseMessage` заполняется строками-заглушками `"asd"`, `operation_id: "asd"` —
  явные времянки, которые попадают в реальные сообщения клиенту.

### 2.7. Кастомный `Deserialize for InstanceFields` реализован неверно

`websocket/messages/option/mod.rs:61-86`: десериализатор извлекает поле `page`, приводит к
нижнему регистру, а затем в `match` сравнивает с литералом `"page"` (именем ключа!), а не со
значением (`"overview"`/`"settings"`). Ветка `"page" => Overview`, всё остальное → ошибка. То есть
Settings через этот путь не распарсится никогда, а Overview распарсится только если значение поля
`page` буквально равно строке `"page"`. Логика перепутана; вариант для Settings отсутствует.
Половина модуля к тому же закомментирована (старый ручной `Serialize`).

### 2.8. Разделение установки и запуска отсутствует

Модель «инстанс» смешивает: сетевую загрузку, регистрацию в БД, сборку launch-аргументов и сам
запуск процесса — всё внутри `Instance::init`. Нет отдельной сущности «установленный инстанс,
прочитанный из БД, готовый к запуску». Из-за этого `run` вынужден переигрывать весь init.
Стоит выделить: `InstanceInstaller` (сеть+ФС+БД) и `InstanceRunner` (сборка аргументов из БД + запуск),
а `Instance` в текущем виде (тянет `version_manifest: Value` и заимствованные поля) разбить.

## 3. Безопасность

### 3.1. Локальный сервер без аутентификации + CORS `*`

`main.rs:44-48` вешает `CorsMiddleware` с `allow_origin("*")` и слушает `127.0.0.1:8080` без
какой-либо аутентификации. Для локального демона это опасно:

- Любая веб-страница в браузере пользователя может слать запросы на `http://127.0.0.1:8080`
  (CSRF/DNS-rebinding). При `Origin: *` браузер не заблокирует ответ.
- Эндпоинты выполняют привилегированные действия: создание директорий по произвольному пути
  (`/init/root` принимает `path` от клиента), запуск процессов, запись файлов.
- `handle_init_root` (`endpoint/mod.rs:28`) создаёт директории по **пути, присланному клиентом** —
  фактически «создай папку где угодно» без валидации.

**Рекомендации:** (1) уйти от TCP-сокета к Unix-domain-socket/Named Pipe с правами доступа только
для текущего пользователя (см. `NATIVE_IPC.md`); (2) если HTTP остаётся — токен в заголовке,
проверка `Origin`, CORS не `*`, а конкретный ориджин клиента; (3) валидация всех путей от клиента
(канонизация + проверка, что путь внутри разрешённого корня).

### 3.2. Загрузка кода/натива с проверкой хеша, но без проверки источника

Хорошо: `download_with_checksum` (`utils/download/mod.rs:54`) считает SHA-1 и сверяет. Плохо:

- SHA-1 криптографически слаб; для целостности от случайных ошибок ок, но не защищает от
  подмены. Mojang/Prism отдают именно SHA-1 — это ограничение апстрима, но стоит хотя бы
  требовать HTTPS и не следовать редиректам на `http://` (сейчас `download_with_checksum`
  слепо идёт по `Location`, в т.ч. потенциально на нешифрованный хост).
- Натива распаковываются `zip_extract` (`launch/natives.rs:15`) без защиты от **zip-slip**
  (путь с `../` внутри архива может записать файл вне `destination`). Для jar от Mojang риск
  низкий, но для сторонних лоадеров/модов — реальный. Нужна проверка, что каждый извлекаемый
  путь остаётся внутри `destination`.

### 3.3. Секрет/окружение в репозитории

`.cargo/config.toml` содержит `DATABASE_URL = "sqlite:/Users/quartix/.sonata/cache.db"` —
абсолютный путь конкретного пользователя закоммичен. `.env` (в `.gitignore`, ок) дублирует
`DATABASE_URL`. Смешение dev-конфигурации compile-time (`.cargo/config.toml`) и runtime (`.env`,
`dotenvy`) запутывает и ломает сборку у других разработчиков. `dev.db` (бинарный SQLite) лежит
в рабочем дереве и не в `.gitignore` (в `git status` виден как untracked) — попадёт в коммит
случайно.

### 3.4. `println!`/`eprintln!` как логирование

Везде вместо структурированного логирования — `println!`. Помимо шума, часть строк печатает
пути/URL/данные инстансов в stdout. Для локального демона это не критично, но стоит перейти на
`tracing` с уровнями и убрать печать потенциально чувствительных данных.

## 4. Производительность и оптимизация

### 4.1. Полное сканирование таблиц при каждой синхронизации

- `download_missing_libs` (`libs/download.rs:33`) грузит **все** строки таблицы `libraries`
  (`SELECT ... FROM libraries ORDER BY name`), потом фильтрует в памяти по хешу. При большой
  общей библиотеке на каждый инстанс это O(всех либ) вместо O(нужных). Правильно — запрос
  `WHERE hash IN (...)` по нужным хешам (или временная таблица нужных хешей + JOIN).
- `extract_manifest_assets` (`assets/download.rs:25`) — то же самое: `SELECT ... FROM assets`
  целиком, затем `HashSet::contains` в памяти. Ассетов бывают тысячи; полная выборка каждый раз
  расточительна.
- В `libraries` нет UNIQUE-индекса по `hash`, поэтому `register_libs` может вставлять дубликаты
  (несколько инстансов качают одну либу параллельно → гонка на вставку). Нужен `UNIQUE(hash)` +
  `INSERT ... ON CONFLICT DO NOTHING`.

### 4.2. Прогресс считается неверно

В `process_futures` (`libs/download.rs:139`, `assets/download.rs:10`) `current` берётся как
`downloaded_libraries.len()` (только реально скачанные в этой сессии), а `max` —
`downloadable_libs_count`/`objects.len()` (все нужные, включая уже закешированные). Если часть
уже в кеше, прогресс никогда не дойдёт до 100%. `current`/`total` должны считаться в одной
системе координат.

### 4.3. Синхронный ввод-вывод в async-контексте (в мёртвом коде)

`java/parse/download.rs` использует `std::fs::File`/`OpenOptions`/`write_all` (блокирующие) внутри
`async fn`. Это блокирует исполнитель. Модуль сейчас **не подключён** (в `java/mod.rs` нет
`pub mod parse;`), т.е. фактически мёртвый, но при возврате в строй даст блокировки. То же в
`utils/metacache/mod.rs` (`std::fs`), тоже почти не используется.

### 4.4. Конкурентность захардкожена

`CONCURRENT_TASKS_COUNT = 100` в двух местах, буфер `16 KiB × 100`. Нет глобального лимита на
сеть/диск между стадиями (либы и ассеты могут суммарно дать 200 параллельных загрузок). Значения
стоит вынести в конфиг и сделать один общий семафор/пул на процесс.

### 4.5. Мелкие неэффективности

- `LaunchInfoBuilder::build` собирает classpath конкатенацией `String` в цикле (кроме бага с
  разделителем) — незначительно, но `Vec<PathBuf>` + `join_paths` и чище, и правильнее.
- `get_version_manifest` (`manifest/mod.rs:12`) качает **весь** глобальный манифест версий, чтобы
  найти одну версию, при каждом запросе — стоит кешировать манифест.
- `str_nth_occurrence` / ручной парсинг URL через `rfind('/')` разбросаны по коду; лучше `url::Url`.

## 6. Структура проекта

### 6.1. Осиротевшие файлы и «раздвоение» модулей

`git status` и содержимое дерева показывают незавершённую реструктуризацию:

- В рабочем дереве есть `src/data/definition.rs` (используется, `EnvVars`) и удалённый из индекса
  `src/data/definitions.rs` — переезд с множественного на единственное число не закоммичен.
- Удалены `src/endpoints/*`, добавлены `src/endpoint/*` (единственное число) — ок, но переходное
  состояние в индексе.
- `src/java/parse/{arch,download,extract}.rs` **физически есть, но не подключены** (`java/mod.rs`
  не объявляет `pub mod parse;`). Они ссылаются на несуществующие `super::{Java, EntryInfo}` и
  при подключении **не скомпилируются**. Это мёртвый код старой реализации Java-загрузчика,
  который надо либо удалить, либо довести и подключить.
- Аналогично в `java/mod.rs` закомментированы `arch/extract/download` — остатки прежней схемы.
- `collect_code.sh` и генерируемый им `all_code.txt` — вспомогательный скрипт, которому не место
  в корне (лучше в `scripts/` и в `.gitignore` для вывода).

### 6.2. Два уровня «websocket»

Есть `src/websocket/messages/**` (определения сообщений + генерация TS) и
`src/instance/websocket/mod.rs` (обёртка `OperationWsMessage` над соединением). Плюс сами
эндпоинты в `src/endpoint/`. Границы «сообщения / транспорт / хендлеры» размыты: например,
`instance_options_sync` (`endpoint/instance.rs:171`) прямо в хендлере хардкодит демо-сообщения
(`"new name"`, `"/Users/quartix/..."`) — это тестовая заглушка в продакшн-роутере.

### 6.3. Дублирование определений

- Дубликат сгенерированного `OptionUpdateMessage.ts` в двух местах (`bindings/websocket/` и
  `bindings/websocket/options/`) — из-за `#[ts(export_to = "./options/")]` на типе, который также
  тянется из корневого `WsMessage`. Клиенту неясно, какой импортировать.
- `detect_os`/`detect_arch` (`utils/system.rs`), `construct_os_name` (`libs/mod.rs`),
  `manifest_osarch` (`java/parse/arch.rs`) — **три разных** способа определить ОС/арку, каждый со
  своим набором строк ОС. Должна быть одна функция-источник истины.
- `download` vs `download_in_json` vs `Download::download_with_checksum` — три пути загрузки;
  первые два (`utils/download/mod.rs:16,23`) частично дублируют функциональность, `download`
  вообще не используется (dead code).

### 6.4. Миграции

`migrations/0003_rename_overview_name.sql` переименовывает колонку, а `0004_revert_overview_name.sql`
её возвращает и дропает `instances.name`. Две миграции гасят друг друга — история «шумит».
Пока проект не в проде, лучше схлопнуть миграции в чистый набор. Плюс:
- `0002` создаёт `instances_settings` с `FOREIGN KEY (java_runtime) REFERENCES java_runtimes(id)`,
  но таблица `java_runtimes` создаётся только в `0005` — FK ссылается на ещё не существующую
  таблицу (SQLite это проглатывает при `foreign_keys=OFF` на момент создания, но это мина).
- `java_runtime` в `instances_settings` — тип `TEXT`, а `java_runtimes.id` — `INTEGER`. FK между
  разнотипными колонками. Определиться с типом id.
- В `0002` таблица `instances` изначально имела `name`, затем его дропнули в `0004`, а `name`
  переехало в `instances_overview` — логично, но подтверждает, что схему стоит консолидировать.

### 6.5. `.sqlx` offline-кеш рассинхронизирован

`SQLX_OFFLINE=true` в `.env`. При этом в `git status` один `.sqlx/*.json` удалён и четыре добавлены —
значит запросы менялись. Если кто-то соберёт без live-БД со старым кешем, `sqlx::query!` даст
несоответствие. Нужно пересгенерировать `.sqlx` (`cargo sqlx prepare`) и закоммитить консистентный
набор, а `DATABASE_URL` для сборки не завязывать на абсолютный путь.

## 7. Генерация биндингов (`bindings/websocket`)

Пользователь отдельно упомянул, что «генерация работает не совсем правильно» — подтверждаю, есть
несколько проблем:

### 7.1. Биндинги устарели относительно кода (дрейф)

`cargo test` перегенерировал часть файлов, и `git diff` показывает расхождения между
закоммиченными `.ts` и актуальными типами:

- `ScanInfo.ts`: было без `id`, стало `{ id: bigint, name, version, loader }`.
- `ScanIntegrity.ts`: было `{ manifest_path, manifest_exist, instance_path, instance_exist }`,
  стало `{ instance_path: string | null }`.
- `ExportTypes.ts`: было `"Sonata" | "Prism"`, стало `"Sonata" | "MultiMC" | "Modrinth"`.
- `SettingsFields.ts`: было `{ dir }`, стало `{ dir, java_bin_path }`.

То есть закоммиченные биндинги **не соответствуют** текущим Rust-типам — клиент, сгенерированный
по ним, будет рассинхронизирован. Генерация «спрятана» в `#[test] export_bindings`
(`websocket/messages/mod.rs:79`), поэтому обновляется только когда кто-то вспомнит прогнать тесты,
и её результат вручную коммитится.

### 7.2. Экспорт как тест — неудачный механизм

- Экспорт запускается как обычный `#[test]`, значит попадает в общий прогон и **молча** перезаписывает
  файлы во время `cargo test` (побочный эффект в тестах — плохо: тесты становятся не
  идемпотентными, меняют рабочее дерево).
- Часть экспорта закомментирована (`options/tests.rs:5-14` — экспорт `OverviewFields`/`SettingsFields`
  в отдельную папку), поэтому набор файлов зависит от того, какие типы «зацепились» транзитивно
  через `WsMessage::export_all_to`.
- `#[ts(export_to = "./options/")]` на `OptionUpdateMessage` даёт **дубликат** файла в
  `bindings/websocket/OptionUpdateMessage.ts` и `bindings/websocket/options/OptionUpdateMessage.ts`
  с разными относительными импортами. Клиент может импортировать «не тот».

### 7.3. Семантические проблемы самих типов

- `InstanceFields` сериализуется во **внешне-тегированный** JSON (`{ "Overview": {...} }`),
  потому что на enum нет `#[serde(tag=...)]`. При этом ручной `Deserialize` (см. 2.7) ждёт
  плоский объект с полем `page`. То есть **сериализация и десериализация несимметричны** — то,
  что сервер отправляет (`{"Overview": {...}}`), клиент по своему же контракту не прочитает
  обратно, и наоборот. Биндинг `InstanceFields.ts` описывает именно внешне-тегированный вариант,
  который расходится с форматом `ChangeRequestBuilder` (`{ id, page, options }`).
- `bigint` в биндингах (`ScanInfo.id`, `OverviewFields.playtime`, `TaskProgress` использует
  `number`) — `i64`/`usize` мапятся в `bigint`, а `usize` в `number`. Смешение `bigint`/`number`
  на клиенте неудобно (нельзя просто `JSON.parse`). Стоит определиться: либо все id в строку
  (для JSON безопаснее), либо явно `#[ts(as = "...")]`.
- `BaseMessage` тащит поля `message_id`/`operation_id`/`request_id` типа `String`, которые в коде
  заполняются `"asd"`/`"todo"` — контракт есть, наполнения нет.

### 7.4. Рекомендации по биндингам

1. Вынести генерацию из `#[test]` в отдельный бинарь/пример (`src/bin/export_bindings.rs` или
   `examples/`) и запускать в CI/через `just`/`make`; в CI — проверять `git diff --exit-code`,
   чтобы устаревшие биндинги ломали пайплайн.
2. Единый корень экспорта, без пересекающихся `export_to`, чтобы не было дублей.
3. Согласовать формат тегирования enum между сериализацией и десериализацией (единый
   `#[serde(tag = "...")]`), убрать ручной `Deserialize`.
4. Зафиксировать политику для 64-битных чисел (строки или `bigint`) и id.

- Система сообщений `WsMessage`/`OperationEvent`/стадии — продуманная модель прогресса
  долгих операций; проблема не в модели, а в наполнении заглушками и генерации биндингов.
- `sqlx` с compile-time-проверкой запросов — хороший выбор (нужно только починить offline-кеш).
- Тесты `maven.rs` и `download` — есть культура юнит-тестов, её надо расширять.
